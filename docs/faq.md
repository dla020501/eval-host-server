# Q&A

**Q1. `reset()`은 언제 호출되는가?**
- 에피소드가 시작될 때 한 번 호출된다.
- 평가 서버가 `reset` 메시지를 보내면 `serve_policy()`가 `BasePolicy.reset(msg)`를 호출하고, 반환 후 `ready`를 응답한다.
- `msg["task_id"]`, `msg["instruction"]`, `msg["conf"]["action_dim"]`을 읽어 에피소드 단위 상태를 초기화하는 자리다.
- 과제 하나가 에피소드 3회이므로 과제당 3번 호출된다.

**Q2. `reset()`이 오래 걸리면 어떻게 되는가?**
- 평가 서버는 `reset`을 보낸 뒤 `ready`를 30초까지만 기다린다.
- 30초를 넘으면 그 에피소드는 `policy_timeout`으로 실패한다.
- 모델 로드와 GPU 초기화는 `reset()`이 아니라 `__init__`에서, 즉 정책 서버를 시작할 때 한 번만 수행한다.
- `reset()`에는 이력 버퍼 비우기, 액션 청크 캐시 초기화, `action_dim` 저장처럼 수 밀리초에 끝나는 작업만 둔다.
- 첫 추론의 JIT 컴파일이나 CUDA 워밍업이 느린 모델은 `__init__`에서 더미 입력으로 한 번 추론해 둔다.
- 이 30초 한도는 `infer()` 호출 1회에도 똑같이 적용된다.

**Q3. 에피소드가 끝나면 연결이 끊기는데 서버를 다시 시작해야 하는가?**
- 아니다. 연결 하나가 에피소드 1회에 대응하며 `done` 후 평가 서버가 연결을 닫는다.
- `serve_policy()`는 계속 수신 대기하고 다음 에피소드는 새 연결로 들어온다.
- 정책 객체는 하나가 모든 에피소드에 재사용되므로 `__init__`에서 로드한 모델도 유지된다.
- 정책 서버가 평가 중에 종료되면 남은 에피소드는 실패로 기록된다.

**Q4. 추론이 느리면 점수에 불리한가?**
- 아니다. 시뮬레이션은 시뮬레이션 시간 기준으로 진행되며 액션이 도착할 때까지 정지한 채 기다린다.
- 벽시계 지연은 점수에 반영되지 않는다.
- 다만 추론 1회가 30초를 넘으면 에피소드가 실패하고, 에피소드 하나에 걸리는 벽시계 시간이 길어지면 평가 전체가 늦어진다.

**Q5. 청크 길이 `T`는 어떻게 정하는가?**
- `T`는 1 이상 `max_chunk_len`(50) 이하이며 초과분은 뒤에서 버려진다.
- 청크 하나는 `T / 20`초의 시뮬레이션 시간 동안 관측 없이 적용된다.
- `T = 50`이면 2.5초 동안 새 관측을 받지 못하는 대신 추론 횟수가 50분의 1로 줄고, `T = 1`이면 매 틱 관측하는 대신 추론 횟수가 12,000회가 된다.
- 반응성과 추론 비용 사이에서 정책에 맞게 정한다.

**Q6. 액션을 전부 0으로 보내면 로봇은 어떻게 되는가?**
- 관절과 리프트는 리셋 포즈를 유지하고 베이스는 정지한다.
- 관절 슬롯은 리셋 포즈 기준 오프셋이고 베이스 슬롯은 속도 명령이기 때문이다.
- `evalhost-demo`가 이 동작으로 연결을 확인한다.
- 관측 `state["joint_q"]`는 절대 관절각이므로 그 값을 액션으로 그대로 보내면 현재 자세가 유지되지 않는다.
- 현재 자세를 유지하려면 에피소드 첫 관측의 `joint_q`를 리셋 포즈로 기록해 두고 `(joint_q - joint_q_reset) / 0.5`를 보낸다.

**Q7. 관측 해상도나 카메라 구성을 바꿀 수 있는가?**
- 없다. `conf["image_size"]`는 `real`로 고정이며 해상도는 실제 로봇 SDK의 기록값과 같다.
- 크기 변경, 자르기, 정규화는 정책 서버에서 수행한다.

**Q8. 연결이 동시에 여러 개 들어오는가?**
- 평가 중에는 한 번에 하나의 에피소드만 진행되므로 평가 서버가 여는 연결은 동시에 하나다.
- 홈페이지의 연결 테스트는 별도 연결이며 평가 중에도 들어올 수 있다.
- `serve_policy()`는 연결마다 스레드를 하나씩 만들고 모든 스레드가 같은 정책 객체 하나의 `reset()`과 `infer()`를 호출한다.
- 그래서 `self.history`처럼 에피소드 상태를 인스턴스 속성에 두면, 평가 도중 연결 테스트가 들어왔을 때 두 연결이 그 속성을 서로 덮어쓴다.
- 평가가 진행되는 동안에는 연결 테스트를 실행하지 않는 것이 가장 간단한 대책이다.

# 트러블슈팅

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 제출 후 정책 서버에 로그가 없다 | 토큰 불일치. 401 거부는 핸들러 전에 일어난다 | 제출 페이지의 토큰과 `--token` 값을 대조한다 |
| 제출 후 정책 서버에 로그가 없다 | 방화벽·NAT·사설 IP로 도달하지 못한다 | 공인 IP와 인바운드 포트 개방을 확인한다 |
| `wss://` 제출에서 접속이 없다 | 등록한 지문과 실제 인증서가 다르다 | 인증서를 재발급하고 지문을 갱신 제출한다 |
| 접속은 되는데 평가가 실패한다 | `infer()` 예외 또는 액션의 NaN·Inf | 반환 shape와 dtype, 값을 확인한다 |
| 오류 코드가 `policy_timeout`이다 | 추론 1회가 30초를 넘었다 | 모델 로드를 `__init__`으로 옮기고 추론을 최적화한다 |
| 로봇이 의도와 다르게 움직인다 | 액션 의미 착오 | [action](protocol.md#action) 절의 레이아웃 표를 확인한다 |
| 청크가 무시되고 로봇이 정지한다 | [동작 규칙](protocol.md#동작-규칙)의 각속도 가드에 걸렸다 | 연속 타깃 간 변화율을 한도 이내로 낮춘다 |
